# Destination Alarm

Android Flutter app for multiple GPS destination alarms (up to ten active at once). You can set several alarms for one destination with different distances or times, and alarms for several destinations. Each alarm has its own progress and can be ended separately. Alerts ring in the order their conditions occur, regardless of which alarm was created first. If one GPS fix reaches two alert areas at once, the closer destination rings first; other triggered alerts wait in the queue. The home screen offers Bus, Metro, Railway, and Other. Bus, Metro, and Railway show mapped stops or stations near the current position, a searched area, or a tapped map point, with selectable list and map pins. Other uses place search or a map pin. The starting alert radius is 500 m for Bus and Metro, and 1 km for Railway and Other. The user can change it from 100–2000 m with presets, a slider, or manual entry in metres or kilometres. The manual unit picker keeps the typed number unchanged; the app validates it against the selected unit. An optional date and time alert can ring at the chosen time or 5, 15, 30, or 60 minutes before it. Repeat is a separate setup option: select any weekdays to reset the alarm on those days, including distance-only alarms. With a time alert, both time and distance reset; the chosen date is the earliest repeat date. Time and distance alerts fire separately in whichever order their conditions occur. Stopping one alert keeps that alarm's other alert active; ending the alarm cancels both of its alerts while other alarms keep running. If both conditions arrive together, one combined alert rings. Saved places, settings, and trip history remain on the device.

Google Maps can share a place to Destination Alarm using Android's Share menu. A loading overlay appears while the app resolves the shared location. The app opens shared coordinates in alarm setup for review. If a short link resolves to a place name without coordinates, the app searches for that place and asks the user to choose a result. When the phone cannot open a short link, the app uses a shared place name if Android supplied one, or opens destination search for manual selection. Direct coordinate links work offline; shortened Google Maps links and place search need internet. Sharing a place does not transfer Google Maps' downloaded offline map.

## Build

1. Install a current stable Flutter SDK and Android SDK (API 36), with Java 17.
2. Run `flutter pub get`.
3. Run `flutter run` on an Android device with Google Play services.

No API key is required. Map tiles come from OpenStreetMap; place search uses Android's device geocoder. Bus, metro, and railway lookup use the public Overpass API and send only the searched area's center coordinates and category when the user opens a transport picker or requests a different area. Bus and metro lookup covers 2.5 km around that point; railway lookup covers 5 km. Those searches require internet, and mapped stop coverage varies. A temporary server failure is retried once, and the picker offers manual Retry if it still fails. Lookup results are cached in memory for ten minutes. A public Overpass instance is appropriate for limited use; a published app with significant traffic needs its own or a contracted POI backend. After the destination is set, the alarm uses saved coordinates, Android's GPS provider, and local sound and vibration; it does not need internet. The active screen leaves the online map hidden by default. An offline basemap is not included. The device's geocoding provider may process search text off-device; the app itself does not store search queries or send GPS history to a server.

## How background alerts work

Before an alarm can start, the setup screen requires precise location, Allow all the time background location, notifications, and unrestricted battery use. It opens the relevant Android settings and rechecks them when the user returns; the alarm controller rechecks before registration. Android's power allowlist is verified directly. On phones whose No restrictions setting does not appear on that allowlist, the user can confirm the setting after opening battery settings. Vendor Autostart controls cannot be verified through a standard Android API. A single native foreground service monitors GPS for all active destinations, checking more often near a destination. Each destination also has a Google Play geofence backup where available. When the distance or optional time is reached, the service plays looping sound and vibration and shows an alarm notification with stop and snooze actions. When multiple alerts are due, the service rings one at a time until each is handled. `AlarmManager` schedules the next time alert, repeat-day activation, or snooze expiry. Alarm configurations are saved in Android preferences. The app restores time scheduling and geofence backups after a device restart or app update, and restores alarm progress into the Flutter UI on launch.

Device power settings or poor GPS reception can delay an alert. The minimum radius is 100 m. Clock alerts use an inexact Android alarm and may also be delayed by battery restrictions. The displayed travel time estimate uses current GPS speed and is unavailable when speed is too low. Force-stopping the app stops background monitoring. A destination alarm should be used with enough radius for the travel speed and should not be the only way to avoid a stop.

## Verification

Run `flutter analyze` and `flutter test`. On a physical Android device, verify foreground, minimized, and locked-screen entry at 100 m, 500 m, and 2 km; notification permission denied; precise/background location denied; GPS disabled; internet disconnected after setup; process and device restart; notification Stop/Snooze; a weekday repeat across two days; early reminders that cross midnight; several alarms for the same and different destinations; and cancellation of one alarm while others continue. Check walking and vehicle travel because GPS timing depends on device and conditions.

Release builds use a private keystore referenced by `android/key.properties`. Keep that file and the keystore outside Git; debug builds do not need them. See Flutter's Android signing guide before publishing.
