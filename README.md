# Destination Alarm

Android Flutter app for multiple GPS destination alarms (up to ten active at once). You can create several alarms for one destination or for different destinations. Each alarm has its own progress and can be ended separately. Alerts ring in the order their conditions occur, regardless of which alarm was created first. If one GPS fix reaches two alert areas at once, the closer destination rings first; other triggered alerts wait in the queue. The home screen offers Bus, Metro, Railway, and Other. Bus, Metro, and Railway show mapped stops or stations near the current position, a searched area, or a tapped map point, with selectable list and map pins. Other uses place search or a map pin. The starting alert radius is 500 m for Bus and Metro, and 1 km for Railway and Other. The user can change it from 100–2000 m with presets, a slider, or manual entry in metres or kilometres. The manual unit picker keeps the typed number unchanged; the app validates it against the selected unit. During setup, the user can reselect the destination and choose weekdays under Repeat. Repeat can also be edited on the active screen. The distance alert is active only on the selected days and resets for each selected day. With no days selected, the alarm is a one-time distance alarm. Saved places, settings, and trip history remain on the device.

Google Maps can share a place to Destination Alarm using Android's Share menu. A loading overlay appears while the app resolves the shared location. The app opens shared coordinates in alarm setup for review. If a short link resolves to a place name without coordinates, the app searches for that place and asks the user to choose a result. When the phone cannot open a short link, the app uses a shared place name if Android supplied one, or opens destination search for manual selection. Direct coordinate links work offline; shortened Google Maps links and place search need internet. Sharing a place does not transfer Google Maps' downloaded offline map.

## Build

1. Install a current stable Flutter SDK and Android SDK (API 36), with Java 17.
2. Run `flutter pub get`.
3. Run `flutter run` on an Android device with Google Play services.

The in-app **Guide & tutorial** is available from Home and Settings. A shareable written walkthrough is in [the user guide](docs/USER_GUIDE.md). Failed stop and place searches show **Retry search** next to the error; it repeats the failed search.

No API key is required. Map tiles come from OpenStreetMap; place search uses Android's device geocoder. Bus, metro, and railway lookup use the public Overpass API and send only the searched area's center coordinates and category when the user opens a transport picker or requests a different area. Bus and metro lookup covers 2.5 km around that point; railway lookup covers 5 km. Those searches require internet, and mapped stop coverage varies. A temporary server failure is retried once, and the picker offers manual Retry if it still fails. Up to 64 area/category results are cached across picker visits in process memory: fresh for ten minutes, with clearly labeled results up to 24 hours old available if refresh fails. Ending the app process clears this cache. Rate-limit responses pause all stop lookups for at least 30 seconds and honor longer Retry-After values. Partial or malformed results are rejected. No server rental or API key has been added; see [server-free search behavior](docs/TRANSIT_SEARCH.md). A public Overpass instance is appropriate for limited use; a published app with significant traffic needs its own or a contracted POI backend. After the destination is set, the alarm uses saved coordinates, Android's GPS provider, and local sound and vibration; it does not need internet. The active screen leaves the online map hidden by default. An offline basemap is not included. The device's geocoding provider may process search text off-device; the app itself does not store search queries or send GPS history to a server.

## How background alerts work

The active screen reports native service health, GPS freshness, and geofence registration status. A saved alarm is not treated as proof that GPS is working. After a reboot, GPS tracking is restored; if an alert was already pending, the tracking notification asks the user to open the app to resume playback. This avoids starting a media playback foreground service directly from the boot receiver on Android 15 and later.

While at least one destination needs GPS monitoring on the current day, the native tracking service renews a bounded partial CPU wake lock so monitoring can continue with the screen off. It releases the lock when no distance alert is ready, GPS is disabled, or the service ends. Alarm audio has its own playback wake lock. Alarm events update the running service directly, and a periodic check recovers a stalled GPS subscription without waiting for the Flutter screen to resume.

Before an alarm can start, the setup screen requires precise location, Allow all the time background location, notifications (including the alarm and tracking channels), Alarms & reminders access, lock-screen alarm access, and unrestricted battery use. It opens the relevant Android settings and rechecks them when the user returns; the alarm controller rechecks before registration. Android's power allowlist is verified directly. On phones whose No restrictions setting does not appear on that allowlist, the user can confirm the setting after opening battery settings. This manual confirmation is held only in memory and expires when the app leaves the foreground or after 15 minutes; it does not bypass notification or lock-screen checks. Vendor Autostart controls cannot be verified through a standard Android API. A single native foreground service monitors GPS for all active destinations, checking more often near a destination. Each destination also has a Google Play geofence backup where available. When the selected distance is reached, the service plays looping sound and vibration and shows an alarm notification with stop and snooze actions. When multiple alerts are due, the service rings one at a time until each is handled. `AlarmManager` schedules repeat-day activation and snooze expiry, as well as time alerts retained from older alarms. Alarm configurations are saved in Android preferences. The app restores time scheduling and geofence backups after a device restart or app update, and restores alarm progress into the Flutter UI on launch.

Device power settings or poor GPS reception can delay an alert. The minimum radius is 100 m. Snoozes and time alerts retained from older alarms use exact alarm-clock scheduling after Alarms & reminders access is granted. Repeat-day activation uses exact idle scheduling. If this access is missing after a restore, the app uses an inexact backup and reports that timing may be delayed; granting access reschedules pending alerts. The displayed travel time estimate uses current GPS speed and is unavailable when speed is too low. Force-stopping the app stops background monitoring. A destination alarm should be used with enough radius for the travel speed and should not be the only way to avoid a stop.

## Verification

Native Android regression tests run with `cd android` then `./gradlew :app:testDebugUnitTest -x :app:compileFlutterBuildDebug`. They use Robolectric and the real Kotlin alarm runtime to cover GPS crossings, queue order, notification dismissal, wake-lock cleanup, reboot recovery, and the restricted lock-screen activity. The first run downloads test dependencies. These JVM tests do not package or install the app and do not replace physical locked-screen travel tests.

The native tracker adjusts GPS sampling to speed and alert radius near a destination. It also checks whether a short, accurate GPS segment crossed a radius between samples; it rejects inference across long gaps, poor accuracy, or implausible jumps. The full-screen notification opens a separate native activity with alarm controls only. Opening the main app follows the normal lock-screen protection.

Run `flutter analyze` and `flutter test`. On a physical Android device, verify foreground, minimized, and locked-screen entry at 100 m, 500 m, and 2 km; notification permission denied; precise/background location denied; GPS disabled; internet disconnected after setup; process and device restart; notification Stop/Snooze; a weekday repeat across two days; destination reselection during setup; several alarms for the same and different destinations; and cancellation of one alarm while others continue. For multiple destinations, create them in reverse travel order, lock the screen, enter the first destination's radius, dismiss its alert from the notification, and continue to the second without unlocking. Both must ring in travel order. Also check that GPS and the monitoring wake lock are released after ending all alarms and while a repeating distance alarm waits for a future day. Check walking and vehicle travel because GPS timing depends on device and conditions.

Release builds use a private keystore referenced by `android/key.properties`. Keep that file and the keystore outside Git; debug builds do not need them. See Flutter's Android signing guide before publishing.

Shared Google Maps link resolution has a total 12-second timeout and a Cancel button. Cancel closes the connection and prevents a late result from changing screens. Only redirect headers are needed, so a stalled response body cannot block the app. Alarm notification controls use a silent notification channel; the native player owns the selected sound and optional vibration to avoid duplicate audio or vibration when it is disabled.

All routes share one native status-event subscription. Writes, GPS/service health changes, and geofence registration changes request a current snapshot; bursts are coalesced. Notification dismissal, snooze, and queued alerts update the ringing screen without two/five-second UI polling. A serialized refresh queue handles events arriving during a read. The subscription stops in the background, and reconnecting reads a fresh snapshot. Manual refresh remains available.

Destination searches share one request generation across place searches and stop lookups. Editing the query, changing transport, choosing a point, or leaving the picker cancels the previous lookup. Stop requests close their HTTP connections; canceled Android geocoder callbacks are ignored. Late results and errors cannot replace the current selection or search, or populate the search cache. Stop lookups also have a total 50-second deadline.

An alarm whose first repeat day is in the future can be saved without acquiring a current GPS fix. Required Android permissions and phone settings are still checked. The native tracker starts acquiring location when that day becomes active. Distance monitoring that starts today still requires an initial GPS fix, including alarms that also have a future time reminder.

Readiness checks include the alarm channel’s high importance, the tracking channel being enabled, full-screen alarm access on Android 14+, and exact-alarm access. Setup shows warnings for zero alarm volume and restrictive Do Not Disturb modes. Android settings remain under the user’s control; the app does not change volume or Do Not Disturb automatically.

Saved places, history, and native alarm storage recover valid entries individually. Damaged JSON can restore a last-good local snapshot; a recent damaged copy is kept locally and a warning appears in Settings. Unrecoverable entries must be recreated. Storage I/O failures are reported and do not become an empty list. Finished native alarms are forgotten only after successful history persistence. History writes and deletion are serialized, and history is limited to the latest 100 unique trips. Clear trip history and Clear saved places delete the corresponding recovery copies while preserving active alarms; Settings also offers deletion of damaged recovery copies. Android cloud backup and device-transfer extraction exclude all app data. These changes do not remove copies from backups made by older app versions.

## Alarm controls and testing

Settings → **Test alarm** previews the selected sound, vibration, and lock-screen notification: a five-second countdown followed by ten seconds of playback, with Stop test available in the notification and preview screen. The preview uses its own notifications, never registers a destination, stops automatically, and yields to real destination alerts. Alarm notification and full-screen permissions are required; GPS and background location are not required for the preview.

Active alarm details show the native last GPS update and accuracy, plus the next selected repeat day. Unknown readings are labeled rather than inferred from a saved alarm.

The alarm menu offers Rename, Edit destination and settings, Duplicate, and Pause/Resume. An optional name is also available during setup. Paused alarms remain saved and listed, but do not trigger GPS, geofence, time, or repeat alerts until resumed. Other alarms keep running. Time reminders that passed while paused are skipped on resume. Edits preserve the alarm ID and progress of unchanged conditions; changing the destination or radius resets its distance condition. Editing is available while active or paused. Duplicate opens a new distance-alarm setup with the original destination, radius, repeat weekdays, name, sound and vibration, and creates a separate alarm only after Start. Improvement-batch progress is recorded in [IMPROVEMENTS.md](docs/IMPROVEMENTS.md).

## Distance display and recovery

Setup and active monitoring show straight-line GPS distance, which can be shorter than the road or railway route. Speed-based estimates use that direct distance. Ringing controls and selection sheets scroll on short screens and with large text. Empty place/stop searches explain how to try another query or area; transit messages show the corresponding search radius. The map warning follows currently rendered tiles, clears after successful loading, and offers **Retry map** without interrupting GPS alarms.

## Older installation migration

`MultiAlarmRuntime` and `MultiTrackingService` now own all destination scheduling, GPS and playback. `AlarmNotifications` owns the common channels. The retired single-alarm runtime has been removed. Old receiver and service class names remain as small compatibility bridges for Android PendingIntents and sticky service intents; they cannot run a second monitor/player.

Migration validates coordinates, preserves time/distance flags, sound and vibration, and never overwrites an existing alarm with the same ID. It retires old scheduling, geofences, services and notifications only after saving the migrated entry. Completed migrations are marked so archived alarms cannot reappear. Invalid legacy data stays preserved and produces a warning. Older versions did not save snooze deadlines; a migrated snooze receives a one-minute replacement deadline. Reboot migration restores tracking first and requires opening the app to resume a pending alert.
